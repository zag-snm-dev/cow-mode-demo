# COW MODE

**欲しい物を、好きなだけカートへ。上限なしの架空のカードで、物欲を思いきり解放するお買い物アプリです。**

「買うモード」と「モードな牛」をかけた名前で、牛のキャラクターが目印です。実際の金銭のやり取りは一切ありません(カードも決済も、すべて架空です)。

- 公開URL:<https://cow-mode.vercel.app>
- 作った人:砂見
- 制作期間:2週間

> 本物のクレジットカード情報は、入力しないでください。入力欄もありません。

## なぜ作ったか

物価は上がっているのに給与は上がらないうえに、コンテンツは溢れかえりあれもこれも欲しいのに買えないと感じる人は多いのではないかと考えました。
せめて**購買欲だけでも、思いきり解放できる場所**があればいいとそう考えて、上限なしの架空のカードで、好きなだけ買い物ができるアプリを作りました。

## できること

- **カード作成**:名前(10字まで)を入力すると、カードの表と裏の画像が生成され、17桁(5-7-5)の架空の番号が付きます。利用上限は「∞」です
- **お買い物**:DummyJSON の商品を5件ずつ表示し(「もっと見る」で追加)、1個ずつカートに入れられます。価格は日本円だけで表示します
- **画像のアップロード**:欲しい物の画像(JPEG / PNG / WebP、5MBまで)を選ぶと、中央を切り抜いた300×300のJPEGに縮小され、プレビューを見ながら、商品名・価格・個数(1〜99)を入力してカートに追加できます
- **カート**:数量の増減、削除、小計と合計、使用カードの表示
- **疑似決済**:1秒の処理のあと、注文を履歴に保存してカートを空にします
- **マイページ**:総決済額、決済回数、決済履歴(新しい順。開くと、画像・名前・円単価・数量)
- **複数タブの同期**:別のタブでの変更(カード作成、カート操作、決済)が、再読み込みなしで反映されます
- **`localStorage` が使えない環境**(プライベートブラウズなど)では、メモリ上で動き、「閉じるとデータが消えます」と表示します

## 画面とルート

| パス | 画面 | 条件 |

| `/` | トップ(使い方 + カード作成) | カード作成済みなら `/shop` へ移る |

## 設計のポイント

### 層の決まり

```
pages  →  features  →  shared
```

依存は、一方向だけです。`shared` は `features` を参照せず、`features` 同士も直接は参照しません(つなぐのは、上の層の `pages` です)。たとえば、カートの画面は、カードの画像を自分で読み込まず、`cardPreview` として親から受け取ります。

### 保存の窓口(`shared/storage`)

`localStorage` を、画面から直接触りません。すべて1つの窓口を通します。

- **zod で、読み出しのたびに検品**します。壊れたデータや、`version` が違うデータは、初期化します
- **書き込む前にも検証**します。アプリのバグで、壊れたデータを保存しません
- **容量超過**は、専用のエラー(`StorageQuotaError`)にして、「容量がいっぱいです」と表示します。失敗したときは、保存前の状態のままです
- **`useSyncExternalStore`** で、画面と結びつけます。保存データが変わると、ヘッダーのバッジ、カート、マイページが自動で更新されます(読み出した値はキャッシュし、変更がなければ同じオブジェクトを返して、無限の再描画を防ぎます)
- **複数タブ**:`storage` イベントで他のタブの変更を受け取ります。通知が届く前に書き込むと、古い内容で上書きしてしまうので、**書き換える直前に、保存先から読み直す**(`loadLatest`)ようにしました。裏に回っていたタブが戻ったとき(`visibilitychange` / `pageshow`)にも、再同期します

### 金額

- ドル建ての商品価格は、**カートに入れる瞬間に、円に確定**します(固定レートで換算し、四捨五入)。カートと履歴は、最初から円で、あとから変わりません
- 画面には、**ドルも為替レートも出しません**(利用者は、日本円での買い物を前提にしているため)
- 小数の誤差を避けるため、いったんセント(整数)にしてから計算します
- 価格の上限は 9,999,999,999円、数量は99個まで。**上限 × 数量でも、`number` で正確に扱える範囲に収まる**値にして、`bigint` を使わずに済ませています(上限のテストで、この前提を見張っています)

### 画像

- 選んだ画像は、**Canvas で中央を正方形に切り抜き、300×300・品質0.7のJPEG**にして保存します。透明な部分は、先に白で塗ります(透過PNGが、黒くならないように)
- 描き直すことで、元のファイルの余計な情報(位置情報など)を引き継がず、容量も数十KBに収まります
- **画像は、1回だけ保存し、カートと履歴は画像IDで参照**します。保存データが、二重に増えません
- 保存できる画像は**全体で50枚**です。履歴が参照している画像は、カートから消しても、削除しません
- 画像を続けて選び直したとき、**古い処理の結果を捨てる**ことで、古い画像が、プレビューに出ないようにしています
- ブラウザの機能(画像の読み込み、Canvas)は、計算の部分と分けて、テストで差し替えられるようにしています

### 決済

- **注文の保存と、カートを空にする処理を、1回の保存にまとめて**います。途中で失敗しても、「履歴だけ残る」「カートだけ空になる」といった、中途半端な状態になりません
- **二重送信は、3段で防ぎます**:(1)処理中は、ボタンと数量・削除を押せなくする (2)フックが、処理中の再実行を無視する (3)カートが空なら、決済しない
- 決済は、`useMutation` で扱います。待ち時間(1秒)の関数を切り出しているので、テストでは、終わるタイミングを、好きに操作できます

### 外部API(DummyJSON)

- **TanStack Query の `useInfiniteQuery`** で、5件ずつ取得します。取得位置(`skip`)は、取得済みの件数から計算し、最後まで取ったら、「もっと見る」が消えます
- 応答は、**zod で検品**してから使います(型は、書いた時点の約束で、実行時に届く中身は守ってくれないため)。使わない項目は、取り除きます
- **5分間は、キャッシュを使います**。お買い物とカートを行き来しても、取り直しません
- 状態を出し分けます:読み込み中(スケルトン)/ 初回の取得失敗(再試行)/ 続きの取得失敗(表示済みの商品は残す)

## セキュリティ

- **入力・外部APIの応答・`localStorage` の読み出し**を、すべて zod で検証します
- 画像のURLは `https` のみ受け付けます。`dangerouslySetInnerHTML` は使いません
- アップロード画像は、形式とサイズを確認し、Canvas で再エンコードしてから保存します
- **Vercel のヘッダー**(`vercel.json`):CSP(`script-src 'self'` など)、`X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options`、`Permissions-Policy`。CSP は、画像の `data:` / `blob:` と、商品の取得先だけを、追加で許可しています
- カード番号は、暗号論的乱数で作り、**Luhn検算に通らない値**にして、実在の番号と偶然一致しないようにしています。本物のカード情報の入力欄は、ありません

## アクセシビリティ・レスポンシブ

- カード作成のモーダルは、`<dialog>` を使い、フォーカスの閉じ込め、Escで閉じる、開いたときの入力欄へのフォーカスを、ブラウザ標準の動作で実現しています
- エラーは `role="alert"`、通知は `role="status"` で、読み上げられます。履歴の開閉は `aria-expanded`、並んだボタンは、商品名つきの `aria-label` で区別できます
- 動きを減らす設定(`prefers-reduced-motion`)では、通知の動きをやめます
- スマホは1列と下部のタブバー、タブレット以上は5列の商品一覧とヘッダーのナビです。操作できる部品は、44px以上にしています
- 画像の `alt`:商品の画像のように、隣に説明の文字がある画像は `alt=""`(飾り)、牛やスクリーンショットのように、説明が必要な画像は、内容を書いています

## テスト

Vitest と Testing Library で書いています。画面は、本物のルート定義を使い、URLを開いた状態から、操作します。

- **ロジック**:円換算の丸め、数量1〜99の制限、カード番号(5-7-5、Luhn不通過、乱数の偏り)、フォームの検証、画像の50枚と参照中の画像の保護、決済(成功・失敗・二重送信)
- **保存**:検証失敗時の初期化、容量超過、使用不可時のフォールバック、他のタブの変更の反映
- **複数タブ**:通知が届く前の書き込みでも、他のタブの変更を消さないことを、再現するテストで確認
- **画面**:アクセス制御、モーダルの操作、カート・決済・マイページの一連の流れ
- **外部API**:msw で DummyJSON を差し替え、追加読み込み、エラー、再試行を確認
- **設定**:`vercel.json` と `index.html` の設定(CSPの許可先、OGPなど)が、崩れていないことを見張るテスト
- Canvas は、テスト環境(jsdom)で動かないため、描画の手順を、偽のCanvasで確認しています。**実際のブラウザでの見た目は、手動で確認**しました

## 既知の制限と今後の課題

- **保存先は、ブラウザの `localStorage` です。** 端末やブラウザをまたいで、データは共有できません。容量は、約5MBまでです
- **決済した画像は、履歴が参照し続けるため、50枚の枠を使い続けます。** 履歴の画像を消す機能は、ありません
- **2つのタブが、まったく同時に書き込むと、後から書いたほうが勝ちます。** `localStorage` に、排他の仕組みがないためです。決済の二重化は、「カートが空なら決済しない」というルールで防いでいます
- 商品データは、外部API(DummyJSON)に依存しています。止まっているときは、エラーと再試行を表示します
- 「もう一度購入」、商品の絞り込み・検索、ログインは、作っていません
- 今後の候補:BaaS(Firebase や Supabase など)の導入で、データの保存先を差し替える。保存の窓口が1つなので、画面側は、ほとんど変えずに済む作りにしています

## 学んだこと

- **状態の置き場所を、先に決める**:保存先を1つの窓口にまとめ、検証・容量超過・複数タブを、そこだけで扱うことで、画面側が、単純になった
- **外部から来るものは、信用しない**:型だけでなく、zod で、実行時に検品する(外部API、`localStorage`、フォーム)
- **テストしやすい形に分ける**:計算(純粋な関数)と、保存、ブラウザの機能を分けると、速く、確実にテストできる
- **非同期の「競合」を考える**:二重送信、古い結果の上書き、通知が届く前の書き込み。起きるタイミングを想像し、テストで再現してから直した
- **アクセシビリティは、あとから足すものではない**:ネイティブの `<dialog>` や、見出し・ラベル・`aria` を、最初から設計に入れる
- **小さく出す**:短いブランチとPRに分けると、レビュー(自分の見直し)と、巻き戻しが楽になる
